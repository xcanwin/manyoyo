# lib/web/ 协作指引

根目录 `AGENTS.md` 的补充，仅在改动 Web 服务端时适用。前端在 `frontend/`，见该目录的 `AGENTS.md`。

## lib/web/server.js（6000+ 行单文件）

与 `bin/manyoyo.js` 一样无分区注释，靠函数名定位：`Grep "^function <名>"`。它是仓库里最大的文件，改动前先确认要落在哪一层（HTTP 路由 / 会话历史读写 / 容器执行 / 流式协议），不要在路由 handler 里堆业务逻辑。

- `resolveYoloCommand()` 委托到 `lib/agent-adapters/index.js`，与 `bin/manyoyo.js` 共用同一份映射，无需分别维护。
- Agent 会话恢复参数：Claude/Gemini → `-r`，Codex → `resume`，OpenCode → `-c`。
- 会话控制事件：`/agent/stream`、`/agent/stop` 通过 `createWebStreamEmitter()` / `appendWebSessionControlEvent()` 写入 `lib/core/event-store.js`（`FileEventStore`），`GET /api/sessions/:name/audit` 导出该会话的事件与投影。
- **`/agent/stream` 的 NDJSON 事件协议是跨前后端的契约**，改一处必须同步另一处：服务端 `lib/web/server.js`、前端 `frontend/src/lib/api.ts` 的 `StreamEvent` + `workspace-panel.tsx` 的事件分支
  - `content_chunk`：token 级增量，前端**追加**；`reset: true` 表示换了一条 assistant 消息、从空白重新开始。只发新增片段，不要改成重发累计全文（几千个增量就是 O(n²) 流量）。
  - `content_delta`：每条 assistant 消息落地时下发一次的权威全文，前端**整体覆盖**。
  - `queue_next`（新增）：这一轮结束后服务端接着发排队的下一条，前端收到后结束这条流、改走恢复轮询（见下面“追加提示词”）。
  - `trace`：**不保证带结构化 `traceEvent`**。stderr 行（`emitStderrTraceLine`）和解析不出 JSON 的 stdout 行只有 `text` + `stream`，前端靠 `toTraceEvent()` 兜底成 `kind="output"` 的事件展示。新增只认 `traceEvent` 的分支等于把自定义 CLI、CLI 报错的输出全吞掉。
  - `ping`：保活心跳，前端忽略。`DEFAULT_AGENT_STREAM_HEARTBEAT_MS` 必须明显小于反向代理的空闲读超时（nginx `proxy_read_timeout` 默认 60s），否则 agent 静默期间流会被 RST，浏览器侧表现为输入框上方冒出 `network error`。
  - token 级增量**不写**事件日志、历史落盘按 `AGENT_STREAM_PARTIAL_PERSIST_INTERVAL_MS` 节流；新增逐事件的落盘/日志动作前先想清楚它会不会被每个 token 触发一次。
- **追加提示词（排队）**：任务进行中用户可以追加提示词，队列存在 `agentSession.queue`（`lib/web/agent-queue.js`，最多 10 条，`when` 为 `now` / `step` / `turn`；`normalizeWebAgentSession` 的字段白名单里要有它，否则落盘后丢失）。接口 `POST /api/sessions/:name/agent/queue`（clientMessageId 幂等；容器被别的会话占着返回 409）、`DELETE .../agent/queue/:id`、`POST .../agent/queue/continue`；`/messages` 带 `queue`。一轮对话的完整流程抽成 `runWebAgentStreamTurn(..., res)`：前端不在线时传 `createHeadlessResponse()` 顶替 `res`，事件照常落盘。每一轮结束（完成 / 失败 / 被追加打断，**用户点停止除外**，由 `stopWebAgentRun` 置 `runState.userStopped`，并把 `agentSession.queuePaused` **落盘**——只记在内存里的话，serve 重启或用户下一次正常发送、那一轮结束后，停止前的排队会被自动发出去；暂停只有 `POST .../agent/queue/continue` 能解除，队列清空时自动解除，`/messages` 带 `queuePaused`）后若队列可以自动发（`agentQueue.shouldAutoDispatch`），先给连着的流发一个 `queue_next` 事件（前端据此结束这条流、改走恢复轮询），再 `setImmediate` 调 `dispatchNextQueued`（同步取出队首并占锁，开不起来就放回队首）。`now` 立即走进程树信号；`step` 在 `isStepBoundary`（一次工具 / 子 Agent / 说明完成）处打断，`agentStepFallbackMs`（默认 120 秒）等不到就退化成 `now`。serve 重启后 `startContainerServices` 末尾调 `resumeQueuedAgentTurns`，把留在队列里（暂停的除外）又没有任务在跑的内容当作 `turn` 发出；发之前用 `buildLiveRunsCommand`（只读，校验规则同停止脚本）看容器里还有没有活着的 Agent 进程，有就不发、排队留给用户——那可能是上一个 serve 的孤儿任务，也可能是同一 HOME 下另一个 serve 实例正在跑的任务，所以只检测不杀。
- **停止 / 打断必须进到容器里发信号**（`lib/web/agent-run-control.js`）：只杀宿主机上的 `docker exec` 客户端，容器里的 Agent 进程会继续跑（实测）。命令被包成 `echo $$ > /tmp/manyoyo-run-<id>.pid; <命令>; exit $?`，**末尾的 `exit $?` 不能省**——命令是最后一条简单命令时 bash 会 exec 替换自己，`/proc/<pid>/cmdline` 里的 `manyoyo-run-<id>.pid` 标记就没了，停止时会因“认不出进程”而不杀（真实容器测出来的，单测里用 `sleep 61; true` 测不到）。PID 文件容器里可写，按不可信输入处理（纯数字、普通文件、命令行带标记才发信号），再按子孙进程树逐级 INT → TERM → KILL。真实的 claude 收到 SIGINT 会正常收尾、**退出码为 0**，所以 `interrupted` 看“发过信号”（`runState.signaled`）而不只是退出码。已验证 Claude 打断后 `-r <id>` 能接上上下文；Codex / Gemini / OpenCode 没有环境验证，拿不到引擎会话 id 时走既有的历史注入降级。
- **子 Agent**：Claude 的 `Agent`（旧名 `Task`）工具生成 `kind: "subagent"` 事件，子 Agent 里的事件带 `parentToolId`（取自 `parent_tool_use_id`）；带 `parent_tool_use_id` 的 assistant 文本不当作主 Agent 的回复。`--forward-subagent-text` 只在 `claude --help` 里有该参数时才加（命令里就地探测，约 50ms，不缓存）。样本 fixture：`test/fixtures/claude-subagent.ndjson`。
- **最终回复的取值**（`resolveAgentFinalOutput`）：原始 stdout 只保留开头 `AGENT_RAW_OUTPUT_MAX_CHARS`（32MB，会话 id 在开头），另外用 `createTailBuffer` 保留结尾（8MB）。最终回复和用量都在结尾：超过上限后只解析开头，会把截断点之前的某条中间说明当成最终回复（每个 token 一行约 260 字节的增量，加上思考 token、子 Agent、大段工具结果，长任务很容易超过）；所以截断时先从结尾提取，提取不到再看开头，用量也优先看结尾（`stdoutTail`）。Claude 以最后一个 `result` 事件的 `result` 为准（后台任务场景结尾有两个 `result`，第一个是中间结论）。提取到的最终回复**不截断**（与流式落盘一致），提取不到才退回原始输出并按 `WEB_OUTPUT_MAX_CHARS` 截断。子进程的 stdout / stderr 必须 `setEncoding('utf8')` 按流解码：逐块 `toString` 会把跨块的中文拆成乱码。测试可用 `agentRawOutputMaxChars` 调小上限；真实样本 `test/fixtures/claude-background-task.ndjson`、`claude-subagent-parallel.ndjson`（claude 2.1.290，已精简）。
- **历史读写在 `lib/web/history-store.js`**：进程内缓存 + 原子写（`writeConfigFileSecure`，0600）+ 合并写盘。读靠 `stat` 的 `ino + mtimeMs + size` 判断缓存是否还有效（别的进程原子替换也能识别）；`loadWebSessionHistory` 返回的是**缓存里的同一个对象**，改了必须 `saveWebSessionHistory`，只读路由不要改它（`getWebAgentSession(..., { create: true })` 会在缓存里留一个未保存的空 agent，只在马上要写的路径里用）。流式过程中的 trace patch 和控制事件走 `{ defer: true }`（只改内存，最迟 `AGENT_STREAM_PARTIAL_PERSIST_INTERVAL_MS` 后落盘）；`process.exit` / serve 关闭会 flush；`result` / `error` 类事件（`WEB_STREAM_FLUSH_EVENT_TYPES`）和所有非 defer 写入立即写盘并带上攒着的内容。`kill -9` 最多丢约 1 秒的 trace。文件解析失败会留一份 `.corrupt-<时间>` 备份再按空历史处理，不要绕过它。磁盘格式只有 `agents.<id>.messages`（不再有顶层 `messages`，紧凑 JSON），老版本（含 `update --rollback`）读取时优先用 `agents`，能读新文件。
- `GET /api/sessions` 以前是同步 IO 大户（逐容器读 + 解析整份历史），现在命中缓存基本是 0 次解析，但新增的同步操作仍要先实测；`buildSessionSummary()` 支持传入调用方加载好的 history，不要重复读。（`docker ps -a` + 批量 `inspect` 实测仅约 90ms，不是瓶颈）
- **`/messages` 是分页 + 增量**（`lib/web/messages-view.js`）：`?limit=`（1～200，默认 60，起点往前对齐到 user 消息）/ `?after=<id>&epoch=<e>`（tail，锚点之后的消息；epoch 不符、锚点不存在或超过 120 条时返回最近一页并标 `mode: "reset"`）/ `?before=<id>`（更早一页）；`GET /messages/<id>/trace` 取完整执行过程。查询参数全部白名单校验，非法返回 400。**稳定前缀约定**：第一条 pending 消息之前的消息不再被修改——违反约定的写操作（删除非 pending 消息、克隆）必须给该 agent 换新的 `epoch`（`removeWebSessionMessage` 与 clone 已处理；新增修改历史消息的写操作要自己判断）。500 条上限从头裁掉**不换** epoch（tail 响应带 `firstId`，前端据此裁掉本地被丢弃的开头）。列表里的 trace 消息会被精简（长字符串截成 200 字符，带 `traceTruncated`），`/audit` 与 trace 接口输出完整内容。
- **控制事件的 seq 以事件日志为准，不是历史快照**：事件日志（`FileEventStore`）每条事件立即追加，历史快照里的 `events` 是合并写盘的，进程被强杀后快照会落后；`appendWebSessionControlEvent` 靠进程内的 `controlEventSeqCache`（首次用从日志读一次，对不上就丢缓存重算）续 seq，从快照取 seq 会在强杀重启后让每一轮对话都抛 `seq 必须连续递增`、serve 直接退出。`FileEventStore.append` 追加前会截掉被强杀留下的残缺末行（否则它变成中间行，之后每次读都抛错）。
- **`clientMessageId` 幂等**：`/agent/stream`、`/agent`、`/run` 收到的 `clientMessageId`（`^[A-Za-z0-9_-]{8,64}$`）会存进 user 消息；同一个 id 已出现在该 agent 的消息里（或同一条请求还在检查与落盘之间，`claimClientMessage`）就不再执行，返回 409 `{ error, duplicate: true }`（`rejectDuplicateClientMessage`）。前端在网络中断后重发放回的内容时沿用原 id，靠它兜住“服务端其实已经收到”的情况；有 `duplicate` 的 409 与“容器忙”的 409 要区分。
- **ETag / 压缩**（`sendJson` / `sendHtml` → `sendBody`）：`/messages` 的 ETag 是 `bootId + 进程内历史版本号 + 查询摘要`（不用 mtime：同一毫秒内两次写入大小相同会误回 304 显示旧内容）；`/sessions`、`detail` 用响应体 sha1；index.html 按文件 stat 缓存并带 ETag。这些响应 `Cache-Control: no-cache`，其余仍是 `no-store`。>1KB 的 JSON/HTML 异步 gzip；**NDJSON 流和 WebSocket 不压缩**（压缩会被缓冲，破坏实时性），`X-Accel-Buffering: no` 必须保留。
- 请求处理链路上注册在**全局认证网关之前**的代码（如 `res.on('finish')` 之类的钩子）必须自带 try/catch：那里抛异常会冒泡成 `uncaughtException`，而 `bin/manyoyo.js` 的处理器直接 `process.exit(1)`——等于未认证请求可打挂 serve。回归用例见 `test/web-server-auth.test.js` 的 `Web Server Robustness`。
- **终端 WebSocket**：`/api/sessions/:name/terminal/ws`，在 `server.on('upgrade')` 里做 Origin 校验 + 认证 + 容器名校验，再交给 `bindTerminalWebSocket()`。上行 `input` / `resize` / `ping` / `close`，下行 `output` / `status`（`ready` / `closed`）/ `error` / `pong`；实现是 `docker exec` 里用 `script` 或 python `pty` 引导出的伪 TTY。**动态 resize**：bootstrap 的 rc 把 `tty` 输出写进容器里 `/tmp/manyoyo-term-<随机id>.tty`；收到 `resize` 后（整数、10～500 列、4～200 行，否则整条忽略；下限比建连初值 40×12 低，因为手机竖屏不到 40 列；节流，同一时刻只有一个 exec）用固定脚本 `TERMINAL_RESIZE_SCRIPT` 在容器里读该文件，内容必须整行匹配 `/dev/pts/<数字>` 才执行 `stty -F`。**这个 tty 文件容器里的进程可写，只能当不可信输入**（脚本只认普通文件、不跟符号链接、最多读 64 字节），用例见 `test/web-terminal-resize.test.js`。降级成非 TTY 时 resize 自然无效。并发上限 `WEB_TERMINAL_MAX_SESSIONS = 20`，每条连接对应一个 `ptyProcess`，`ws` 关闭即 `SIGTERM`——所以前端任何「卸载终端组件」的改动都等于杀掉用户正在跑的 shell。
- 空闲保活是 `/agent/stream` 那条心跳规则的同类问题，**两个入口都要守**：终端侧服务端每 `WEB_TERMINAL_PING_INTERVAL_MS`（30s）发 WebSocket ping 帧，连续 `WEB_TERMINAL_MAX_MISSED_PONGS`（3 次，约 90s）无 pong 才判死；前端另发应用层 `ping`（浏览器 JS 发不出 ping 帧，上行需要自己造流量）。判死阈值不要收紧到一个周期：手机切后台会让连接短暂挂起，误杀等于用户的 shell 没了。升级后的 socket 还要 `setTimeout(0)` + `setKeepAlive`，解除 HTTP 侧空闲超时。
- 新增接口/页面必须走全局认证网关，禁止在业务路由里零散补认证；匿名白名单见根 `AGENTS.md` 的安全约束。
- **系统提示词**（`lib/agent-instructions.js` 唯一数据源，`buildWebAgentExecCommand` 的 `options.instructions`）：全局配置（`agentInstructions` + 两个 `agentInstructions{Builtin,Custom}Enabled` 开关，`composeSystemPrompt`）只决定**新建容器时的初始内容**；创建时（请求 `systemPrompt:{enabled,text}`，没给就现算）存进容器状态目录 `system-prompt.json`，之后只能经 `/api/containers/:name/system-prompt` 改，改系统设置不影响已有容器。每次执行时读该容器的文件（`readContainerSystemPrompt`），旧容器没有文件就退回按当前全局配置现算；claude 用 `--append-system-prompt`、codex 用 `-c developer_instructions=<TOML 字符串>`、opencode 把说明写进容器 `/tmp/manyoyo-agent-instructions.md` 再经 `OPENCODE_CONFIG_CONTENT` 合并（1.19.3 实测与用户的 instructions 拼接）；gemini 只有 `GEMINI_SYSTEM_MD` 这种整体替换，不注入。用户模板里已有同名参数 / 变量就不注入；用户追加的文本去控制字符、把 `{prompt}` 拆开（否则会被模板替换成提示词）。CLI 的 `manyoyo run` 是交互终端，不注入。
- **会话标题**：claude 交互模式写 `ai-title`、`/rename` 写 `custom-title`（优先），**`-p` 下实测不生成 `ai-title`**（2.1.290，3 轮）。每轮结束后 `refreshWebAgentTitle` 在后台只读会话 jsonl 尾部 256KB（session id 按 UUID 校验），失败静默不写日志；`firstPrompt` 在第一次追加 Agent 用户消息时记下（历史会被裁剪，不能现算）。这些字段与 `pinned`、`slashCommands` 都要同时加进 `createEmptyWebAgentSession` 和 `normalizeWebAgentSessionRecord`，否则落盘丢失。
- **斜杠命令候选**（`GET .../slash-commands`）：来自 claude 每次运行 init 事件的 `slash_commands` / `skills` / `terminal_slash_commands`，只列 skill 和 `HEADLESS_BUILTIN_COMMANDS`（`-p` 下逐个实测过；`compact` 在 `-p` 下不压缩，别加回去）。
- **改动视图**（`lib/web/git-changes.js`，`GET .../git/changes`、`.../git/diff?path=`）：按需执行、不轮询；仓库和 git 配置由容器控制，命令里关掉外部 diff / textconv / fsmonitor、`GIT_OPTIONAL_LOCKS=0`、输出有上限；diff 的 path 必须出现在服务端重新取的改动列表里，`-` 开头和换行 / NUL 一律拒绝。

## 容器管理接口

`lib/web/container-manage.js`（路由工厂，由 `handleWebApi` 追加进路由表）：`/api/containers/:name/{env,autostart,autostart/run,autostart/log,network,network/allow,network/denied,expose}` 与 `/api/containers/orphans`。旧容器（无 `manyoyo.id`）GET 返回 `{legacy:true}`、写返回 409。`PUT env` 用 `If-Match`（etag）防止覆盖容器内的修改；放开类改动（切到 `custom`、新增很宽的允许规则、非 loopback 暴露）服务端也要求 `confirmRisk:true`；`network` 是 v2 规则表（`outbound` / `inbound`，旧 v1 读取时自动转换，`@container:<名称>` 保存时换成 id）。serve 运行时就绪后 `startContainerServices` 订阅 `<runtime> events`（start / die）补下发规则、拉起 `autostartOnServe` 容器、恢复端口暴露；事件流断开重连（运行时重启）后 `reconcileContainerServices` 再对账一次；过滤代理是 sidecar 容器（`lib/egress-sidecar.js`），由网络管理器 `ensure()` 保证在运行，不在 serve 进程里。`GET network` 带 `denied`（最近被拦截，已放行的不列）、`derived`（别的容器入站放行本容器产生的出站派生行）与 `peers[].ip`；`network/allow` 在出站用户规则最前插入允许域名行；`/agent/stream` 进行中 `createWebDeniedNotifier` 每 2 秒读一次拦截记录，有新域名就推一条 `trace`（只有 `text`，同一域名同一轮一次）。所有 exec 经 `spawnContainerExec`（env 临时文件在子进程 close 时删）。

## 保存不覆盖别人的修改（If-Match）

`PUT /api/config` 和 `PUT /api/sessions/:name/fs/write` **必须**带 `If-Match`，缺少返回 428（报错统一用 `STALE_PAGE_MESSAGE`“页面已更新，请刷新页面后再保存”：现在的前端总会带上 If-Match，走到这里的只有升级前就打开、还没刷新的旧页面，提示要让用户知道怎么办），版本不一致返回 409 `{ conflict: true }`（与容器环境变量 `PUT env` 同一套约定）。`GET /api/config` 的 `etag` 是**磁盘原文**的 sha256（不是脱敏后的 `raw`：只改了密钥时脱敏文本不变，用它算版本就识别不出来），响应里只有哈希；409 的响应体带最新的 `buildSafeWebConfigSnapshot`（含新 `etag`）。配置文件的“读文件 → 比对版本 → 写文件”必须在同一个同步段里完成（中间不能有 `await`，并发请求测试 `test/web-config-etag.test.js` 守着）。`fs/read` 返回内容的 sha256 `etag`（只给 2MB 以内的可编辑文件算），`fs/write` 在容器内的脚本里写入前重新算当前内容的哈希，不一致就返回 `conflict`、服务端转成 409；容器内“比对”和“写入”之间仍有一个极短的窗口（同一个脚本里的两条语句），可以接受。其余写配置文件的接口（`/api/setup/*`、`quick-chat-config`、CLI 的 `build`/`init`/`setup`）都是“读当前磁盘内容 → 局部修改 → 写回”，不会盖掉别人的修改，不需要版本号。**新增写配置文件的接口时，要么走局部修改，要么也带 If-Match。**

## lib/web/index.html

前端构建产物（`npm run build:web`，已 `.gitignore`），由 `loadIndexHtml()` 按文件 stat 缓存读取（文件变了才重读），`/` 与登录页 `/auth/login` 共用。服务端不托管其它前端静态资源，别往 `lib/web/` 里放散装 js/css。

## 测试

- 浏览器 E2E：本机有 `http_proxy` 时，连本地 CDP / serve 要 `env -u http_proxy` 或 `--noproxy '*'`；Playwright `connectOverCDP` 的页面始终显示为有焦点、可见，焦点和可见性要靠覆写 `document.hasFocus` / `visibilityState` 并派发事件来模拟；假 Agent 的开关用唯一令牌，因为服务端会把最近的对话注入 prompt。

Web 相关改动优先补 `test/web-server-auth.test.js`；涉及认证时至少验证未登录 `401`、登录成功可访问、登出后失效。
