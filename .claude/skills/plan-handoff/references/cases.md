# 历史案例（正面 / 反面）

只收录“方案写法明显失败或明显奏效”的案例，用来帮助理解 SKILL.md 里的原则。格式：情境 → 方案怎么写的 → 结果 → 原则（对应检查清单里的条目）。具体命令和路径只是当时的情况，不要原样照搬到其他项目。

## 验证与 TDD

- **反｜TDD 只写口号**（chat-sync-perf，第一轮）：方案写了“先写失败用例再修”，但没要求交付证据。执行者把测试交给子 agent，测试和实现一起写，结果 6 个新模块的测试没有一条在旧代码上看过红灯，还要单独开一轮回溯补证。→ 原则：TDD 写成交付物（红灯证据表 + 变异验证）。
- **反｜测试工具伪装环境**（chat-sync-perf）：验收“窗口不在前台时降频”，用 Playwright `connectOverCDP` 附加的页面始终显示为有焦点、可见，真实的窗口切换没法复现。执行者还误判成“本机没有窗口管理器”。→ 原则：关键环境先验证测试手段本身有效。
- **反｜测试替身被真实输入触发**（chat-sync-perf）：假 Agent 根据提示词里有没有 `quick` 决定提前结束，但服务端会把历史对话注入提示词，结果 5 步就结束了。→ 原则：替身的开关用唯一令牌。
- **反｜红灯证据表是誊写的**（chat-sync-perf 第三轮）：方案要求逐条填红灯证据表，但没要求附上命令和原始输出。表里有 8 条配置接口用例被标成“旧代码上也通过”；复盘时在旧提交上重跑，这些用例实际都失败了（例如 `Expected: 428, Received: 200`）。测试本身是有效的，但证据表结论和实际不符。→ 原则：证据表要附上可复现的命令和失败输出片段；复盘时抽查几条重跑。
- **正｜证据表附上复现命令**（release-autopilot）：复盘时按表里的命令在旧提交上抽查重跑，结果与记录一致；执行者也如实标出了一组没做变异验证的用例。和第三轮“誊写的证据表”形成对照。
- **正｜改动前后都有数据**（chat-sync-perf）：方案要求先采集基线再动代码，并写了放弃门槛。交付时每一项都有改动前后的对比，收益一目了然。
- **正｜用成果真实跑一遍**（release-lifecycle）：用新的发布流程真实发了一版，暴露出好几个自测发现不了的问题。
- **反｜新手试用绕过真实入口**：试用的子 agent 自己 `exec` 开 shell，绕开了用户真实会用的网页终端和对话，文档里的卡点没测出来。→ 原则：试用要走用户真实入口，文档改完要再试一次。

## 状态、缓存与送达

- **反｜没收到确认就当作没送达**（chat-sync-perf）：方案规定“断网且没收到 meta 就把提示词放回输入框”。但服务端在耗时的准备阶段之前就已经存下了消息，所以会误报“没发出去”，用户再发一次就执行了两遍。→ 原则：恢复或重试之前先按幂等键对账。
- **反｜失效条件在稳态下频繁触发**（chat-sync-perf）：方案要求“历史超过 500 条、从头裁掉时更换 epoch”。达到上限之后每条新消息都会触发一次裁剪，增量同步就退化成每次全量。执行者改成用 `firstId` 处理。→ 原则：逐个问失效条件在稳态下多久触发一次。
- **正｜ETag 不用 mtime**（chat-sync-perf）：方案事先写明“同一毫秒内两次写入、大小相同会误判为没变化”，要求用进程内版本号，并配了专门的用例。执行中没有出问题。
- **正｜单飞的主动触发不能丢**（chat-sync-perf）：方案点名“只跳过、不补跑会漏掉流结束后的那次对账”，执行时据此分开处理定时触发和主动触发。
- **反｜同名字段含义随模式变化**（chat-sync-perf）：`firstId` 在分页模式下指本页第一条，在增量模式下指整份历史的第一条，方案没有区分，前后端只能各自对齐。
- **反｜参数下限脱离真实调用方**（chat-sync-perf）：方案让终端 resize 沿用建立连接时的下限（40 列），而手机竖屏不到 40 列，这样恰好会复现要修的“行尾被切”问题，是审查时才发现的。

- **反｜“顺手修”只修了报告的那一个实例**（chat-sync-perf 第二轮）：用户让执行者顺手修“系统设置保存后快捷对话被改回旧值”。执行者只把快捷对话的两个字段并回去，没处理根因：保存会无条件覆盖整个文件。同一个弹窗里的软件源面板有同样的问题，没有修。兜底路径还会悄悄丢掉用户其他没保存的修改；测试只覆盖了纯函数，也没有记录进 FEEDBACK。→ 原则：先找根因类别、列出同类实例；降级路径不能更糟；追加的需求按同样的标准做。

- **反｜编排条件没有真值表**（release-autopilot）：方案只给了条件表达式，没要求逐格验证。结果镜像 job 被跳过时，“跳过”沿依赖链传下去，草稿、挂资产、公开全被跳过，而整次运行的结论仍是 success（假成功）。静态代码审查也没发现，是第二次试跑才暴露的。→ 原则：编排类改动附“上游结果 × 是否运行”真值表，并用试跑覆盖。
- **反｜提速项没有先量单项耗时**（release-autopilot）：方案预期“挂资产并入流水线”能从 3.6 分钟降到 1.5 分钟，实测却是 3.4–11.7 分钟，因为同一次运行里重新下载 6GB 产物受 runner 网速影响很大。方案还要求“冒烟安装放进构建 job”，没先量 Intel 上冒烟要 6.7 分钟，执行者只好把它挪出去。最后“公开 ≤15 分钟”的目标没达成（实测 24.5 分钟）。→ 原则：关键路径上的每个新步骤或搬迁项先给出实测数；目标写明测量条件。
- **正｜真实发一版暴露了自测发现不了的问题**（release-autopilot）：dogfood 之后发现 `--status` 永远显示“尚未验证”、失败日志截到的是收尾清理、进行中阶段的耗时不刷新，都当场修好了。

- **正/反｜性能问题只要求“先分段量”还不够**（autopilot-2）：方案要求先拆耗时，这一条救了场；但方案把嫌疑写成“自校验的哈希命令”。实际 `shasum` 15 秒，管道前端 macOS 自带的 `tail` 读 2GB 要 168–235 秒；改成 `dd + cat` 后，Intel 完整安装从 494 秒降到 39 秒，所有 macOS 用户都受益。执行者如果只照方案对比 shasum 和 openssl，就会得出“不改”的结论。→ 原则：管道的每一段单独计时，不要预设瓶颈。
- **反｜“产物可用”没打开就下结论，复盘也没抽查**（release-autopilot → autopilot-2）：上一轮声称汇总里的失败日志“内容可用”，实际文件只有标题（运行中读不到同一次运行的 job 日志）。复盘时我只抽查了测试，没打开产物，下一轮才暴露。→ 原则：复盘要打开一个关键产物；凡是依赖“运行中读取外部数据”的设计，先验证接口在运行中的行为。
- **反｜授权推送没写推送范围**（autopilot-2）：执行者 `git push origin main` 时，把本地一个不属于这次任务的提交（复盘文档）一起推了出去。→ 原则：授权推送时写明范围，推送前核对 `origin/main..main`。
- **正｜目标时长按分解推算**（autopilot-2）：方案把“公开 ≤15 分钟”分解为 构建约 10 + 合并清单约 0 + 公开前验证约 2 分钟，推算与干净运行的实测一致（12.7 分钟）。上一轮的目标没有分解，所以没达成。

- **反｜把“替换已发布文件”当成原子操作**（code-update）：方案让 CI 用 `gh release upload --clobber` 替换滚动预发布里的清单，只规定了“包先传、清单最后传”，默认替换是原子的。实际是先删后传，读者在空窗里会拿到 404，审查时才补上客户端重试。→ 原则：替换共享资源时，把“替换过程中读者看到什么”当成真值表里的一格。
- **正｜对外资源的设计先实测会不会伤到现有工具**（code-update）：方案原想每次构建移动 `code-main` tag，出方案时在临时仓库实测发现 `git fetch --tags` 会以退出码 1 失败，而发布控制台正好多处执行它；改成 tag 固定指向根提交。真实运行后发布流程、`releases/latest`、npm 发布都没受影响。
- **反｜改了被测试替身包着的函数，方案没点名替身**（code-update 第二轮）：方案让 `build.js` 新增一条 `git rev-parse HEAD`，检查清单里有“盘点测试替身”，但方案没落实：既有的假 `run` 对未知命令返回空串，8 个旧用例因此失败；测试用的代码版包缺 `source.commit`，本地复用测不了。执行者边跑边补。→ 原则：新增外部调用或新读字段时，方案点名要改的替身和夹具。
- **正｜预建 FEEDBACK 骨架**（code-update 第二轮）：规划者建好九节骨架后，执行者九节全部填写，偏差和遗漏各自成节。
- **反｜规则要求每条新用例都有红灯，与守卫用例冲突**（code-update 第二轮）：“提交号缺失 / 不同 → 照常下载”这类用例在旧代码上本来就该通过，执行者只能在表里注明“不是红灯”。→ 原则：守卫用例单列，用变异证明。
- **反｜FEEDBACK 结构只写在方案末尾**（code-update；agent-steering 也有类似情况）：方案在最后一节列了九节结构，执行者只交了其中六节，“被证实 / 偏差 / 遗漏”三节没写，偏差散落在建议里。问题在方案：结构只是一段文字，不是可检查的交付物。→ 原则：规划者直接建好 FEEDBACK 骨架，执行者只往里填。

- **反｜方案里两条规则互相矛盾，用户意图只记在内存里**（agent-steering）：方案一边写“用户停止后排队保留、不自动发”，一边写“serve 重启后，队列有内容就按这一轮结束后发送”。执行者照做，“停止”只记在这一轮的内存里，结果 serve 重启后、或者用户再正常发一条、这一轮结束时，停止前的排队都会被自动发出去。复盘时才发现并修好（暂停落盘）。执行者的反馈也没按要求写红灯证据表，只列了三条。→ 原则：用户意图要落盘，并逐条核对重启后、下一次操作后是否仍然成立。

- **反｜用户在别的环境验证过，就写成“首选写法”**（user-needs）：用户说在自己终端里 `printf '\a' > /dev/tty` 能响，方案据此把写 `/dev/tty` 定为首选。实测发现 hook 没有控制终端，而且这种写法在 dash 下会让 Stop hook 以退出码 2 结束，Claude 反复重跑（输出涨到 41KB）。幸好方案要求“首选也要 pty 实测”，执行者拦住了。→ 原则：别人在另一个环境里验证过的命令，在目标环境里仍然是【推测】；涉及退出码语义的命令，要写出失败时的危害。
- **反｜性能实验直接在真实仓库上做**（user-needs）：方案让执行者在“manyoyo 仓库本身”上测“改 1 个文件再拍快照”的耗时，执行者往一个被跟踪的文件末尾加了一行，之后被一个 docs 提交顺手带了进去。→ 原则：会改文件的实验，方案要求先复制到临时目录。
- **反｜追加需求只跑单测就提交，修一个回归又引出另一个**（user-needs）：升级 `imageVersion` 暴露出“helper 固定用默认镜像，本地却没有”的问题；执行者改成用容器自己的镜像，却没想到旧镜像里没有 nft，并且只跑了 `test:unit`，集成用例的失败要到复盘时跑完整 `npm test` 才发现。→ 原则：改“用哪个版本 / 哪个镜像”时，列出各版本的能力差异；追加需求的验收与正式项相同（含集成测试）。
- **反｜环境规格凭印象写**（user-needs）：方案写本机是 x64，实际是 aarch64，执行者据此误判过“镜像在仿真运行”。→ 原则：环境规格用命令现测（`uname -m` 等）。

- **正｜先修挡发布的回归，再做增强**（user-needs PLAN2）：方案把“回归、误提交、完整测试全绿”排在增强项前面，并写明“到这一步可以交给用户决定发布”。执行者照做，旧镜像无 nft 的回归在发布前修好，而且有真实回归证据。
- **反｜没有方案的迭代轮，交付标准悄悄降级**（user-needs 第三轮）：用户在对话里逐条提需求，执行者连做 20 多个提交、直接推 main，其中包括会真删用户目录的“磁盘占用”。后端测试和实现一起写，没有红灯；判定规则只拿自己机器的数据验证，被用户的真实环境推翻了三次；复盘时还发现“查得到挂载就跳过历史”会把在用的目录判成可删。→ 原则：删除用户数据的功能一律先出方案，判定规则按“宁可删不掉”取并集，并用真实环境的挂载与配置做用例。
- **反｜修了报告的入口，同根的其它入口没修**（user-needs 第三轮）：“容器被删后用 serve 启动目录重建”只修了重建这一条路径；`POST /api/sessions` 不带 hostPath 等三处仍默认用 serve 启动目录。→ 原则（同“顺手修只修了报告的那一个实例”）：方案要求 `grep` 出同一个默认值的所有使用处，逐处登记“改了 / 不用改及原因”。

- **反｜方案给的复现写法，在旧代码上其实不红；去掉兜底时没提老数据**（user-needs PLAN3）：方案让执行者用“挂载 Source 是符号链接”复现误判，但旧代码会先解析符号链接，这种写法本来就判对了，真正会漏的是“解析后对不上的另一种写法”。方案去掉“退回 serve 启动目录”这个兜底时，也没提醒有老用例和老数据（没有 runtimeSnapshot 的历史）依赖它。两处都是执行者在完整测试里才发现的。→ 原则：方案里写的复现步骤，规划者自己先在旧代码上跑一遍；删除兜底时，列出依赖它的老用例和老数据，并写明它们之后的行为。

## 信任边界与依赖

- **正｜对照实验找出默认安全策略**（playwright-usability）：同一个服务分别绑定 127.0.0.1 和 0.0.0.0 做对照，发现 Playwright 1.64 起只绑回环地址时会校验 Host。
- **反｜身份可伪造**（container-manage-2）：sidecar 按来源 IP 识别容器，但 docker 默认带 `NET_RAW`、podman 没有，容器可以伪造来源 IP。必须按运行时逐个列出默认能力，并实测伪造用例。
- **反｜高信任方读取低信任方可写的文件**：容器里的 `/etc/hosts`、挂载目录里的文件、终端的 tty 记录文件，容器内的进程都能改写，必须按不可信输入处理（符号链接、FIFO、超大文件、伪造内容）。
- **正｜非官方产物要求可复现构建**（browser-antibot）：从公开源码复现 tarball，以 `npm pack` 的 sha512 与 registry 上的 integrity 是否一致作为判据，不一致就不采用。
- **反｜名字规则只给正则、不给反例**（code-update）：分支名会拼进 tag、URL 和本地路径，方案只写了一个正则加“不含 --”，`a/../b`、`a//b`、结尾 `/` 都能通过，执行者写测试时才补上。→ 原则：凡是会拼进路径或 URL 的名字，方案要列出必须拒绝的反例。
- **反｜删命令时忽略隐含副作用**（browser-antibot）：删掉 `install-deps` 时，没注意到它会顺带执行 `apt-get update`。

## 收紧类功能与界面

- **反｜收紧时误伤合法链路**：默认拒绝之后，模型服务、内置浏览器、CDN 被拦。每个预设都要用真实 Agent 跑一遍，只用 curl 验证规则不够。
- **反｜两套语义重叠的概念并存**（container-manage）：界面上出现了两套 env，到验收阶段才合并，十几处界面问题被人工纠正。→ 原则：在方案阶段就合并概念，审查时同时看视觉和文案。

## 流程与授权

- **反｜把“授权发布”当成“豁免检查”**：用户授权了发布，执行者顺手代勾了真机检查。→ 原则：豁免范围要写明具体到哪个版本、哪一项、哪个提交。
- **反｜新增共享资源漏了枚举点**（container-manage-2）：新增的 sidecar 容器在列表、孤儿判断、卸载等按名字或镜像枚举容器的地方被当成了用户容器。
- **反｜旧的常驻进程抢资源**：测试时旧版本的 serve 或 watcher 还在运行，和新代码抢同一批资源。
- **反｜缓存提速估算偏乐观**（release-lifecycle）：按命中缓存的数据估算收益，但缓存有作用域，分支写入的缓存 main 读不到。→ 原则：按冷启动数据估算。
- **反｜测试污染用户目录**：在 Jest 里改 `process.env.HOME` 不影响 `os.homedir()`；HOME 变量为空时，状态会写进当前目录；`build` 会把配置写回用户的真实配置文件。
