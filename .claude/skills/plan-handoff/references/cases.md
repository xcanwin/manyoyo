# 通用案例（已抽象，不含任何项目信息）

每条的格式是：情境 → 结果 → 原则。这里只写**脱敏后**的通用经验，不写项目名、产品名、命令、路径、数据源名或研究内容。带细节的原始案例放在各项目自己的 `.claude/plan-handoff.local/cases.md`，不随 skill 分享。

## 验证与测试

- **反｜TDD 只写口号**：方案写了"先写失败用例"，但没要求交付证据，结果新测试一条都没在旧代码上红过。→ 把 TDD 写成交付物：红灯证据表加变异验证。
- **反｜证据表是誊写的**：证据表没附命令和原始输出，复盘重跑时发现结论和实际不符。→ 证据表要附可复现的命令和失败输出片段；复盘时抽查重跑。
- **反｜测试工具伪装了环境**：自动化框架附加上去的页面永远显示"有焦点、可见"，要测的状态根本复现不了。→ 关键环境先验证测试手段本身有效。
- **反｜测试替身被真实输入意外触发**：替身按输入里有没有某个普通词来切换行为，真实流程恰好会注入这个词。→ 替身的开关用唯一令牌。
- **反｜假替身骗过了单测**：用假的流写绿了单测，换成真实子进程才发现读端不读完就会堵住、断开连接会崩掉整个服务。→ 包装外部进程或协议时，第一步先用真实依赖跑通最小闭环。
- **反｜检验器本身没做灵敏度检验**：前视检测、注入检验在"被测函数坏掉"时照样显示通过；同样的错误连续出现了两轮。→ 任何检验器都要有一条"换成恒等或坏的实现，检验必须失败"的用例；注入要作用在被测流程的输入上。
- **反｜变异验证假绿**：字节码缓存按"修改时间（秒）+ 文件大小"判断是否过期，长度相同的变异还原后会残留旧版本。→ 变异测试禁用字节码缓存，并清掉缓存目录。
- **反｜新手试用绕过了真实入口**：试用的子 agent 自己开 shell，绕开了用户真正会用的界面。→ 试用要走用户的真实入口，文档改完要再试一次。
- **正｜改动前后都有数据**：先采基线再动代码，并写好放弃门槛，交付时每一项都有对比。
- **正｜用成果真实跑一遍**：用新做的流程真实跑一次，暴露出好几个自测发现不了的问题。
- **反｜"产物可用"没打开看就下了结论**：声称可用的产物，实际只有标题。→ 复盘时至少打开一个关键产物看实际内容。
- **反｜守卫用例和"每条都要红灯"冲突**：有些用例在旧代码上本来就该通过。→ 守卫用例单列，用变异证明它能失败。
- **反｜真实设备才有的问题，方案没写模拟复现不了时的退路**：模拟环境里旧代码也表现正常，只能按源码修。→ 方案事先写明"模拟复现不了时以什么为准、留什么给用户真机抽查"。
- **正｜旧版本并排运行做对照采样**：检出旧提交另起一份实例，界面问题改前改后都拿到了数字对照。
- **正｜改动前先把真实组合各跑一遍基线**：拿到"改动前失败 / 改动后成功"的对照表；规划时自己用真实凭据实测，还发现了之前没人发现的问题。
- **正｜按比例缩小阈值，再加直接测量**：要凑够真实超时需要的数据量放不下，就另起一份把阈值缩小的实例，并直接测量关键量，问题得以确定性复现。
- **正｜推测的机制配了对照组**：对照组推翻了推测，得出更准的根因。推翻与证实一样有价值，执行者因此如实报告了被推翻的嫌疑。
- **反｜假设写了备选，却没指明在哪种数据形状上验**：在"体积小、条目极多"的数据上，假设不成立。→ 假设按数据形状的极端值（大而少、小而多）分别验证。
- **反｜设计改了行为，判据没跟着改**：方案只点名了一条要改的判据，其余靠执行者自己判断。→ 方案列出"判据随设计怎么改"；修复前后的对比工具要兼容新旧接口。

## 状态、缓存、送达

- **反｜把"没收到确认"当成"没送达"**：重试导致执行了两次。→ 恢复或重试之前，先按幂等键对一次账。
- **反｜失效条件在稳态下频繁触发**：达到上限之后每次都触发全量。→ 逐个问每个失效条件在稳态下多久触发一次。
- **反｜同名字段在不同模式下含义不同**，方案没区分。→ 同名字段在每种模式下的含义分别写清。
- **反｜参数边界脱离真实调用方**：下限比真实设备的最小值还大。→ 参数边界用真实调用方能产生的极值来核对。
- **反｜用户意图只记在内存里**：重启以后，"停止"就失效了。→ 意图要落盘，并逐条核对重启后、下一次操作后是否仍然成立。
- **正｜变更检测不靠修改时间**：方案事先写明"同一时间粒度内两次写入、大小相同会被误判为没变"，要求用进程内版本号并配专门用例，执行中没出问题。
- **正｜合并并发时主动触发不能丢**：方案点名"只跳过、不补跑会漏掉收尾那次对账"，执行时把定时触发和主动触发分开处理。
- **反｜改了计数规则，却没修正已经落盘的旧状态**：→ 方案要同时写出"修正已落盘状态"这一步。

## 根因与同类实例

- **反｜"顺手修"只修了被报告的那一个**：同根的其他入口和面板仍有问题，兜底路径还会悄悄丢数据。→ 先找根因类别，`grep` 出同类的所有实例，一起修；降级路径不能比原问题更糟。
- **反｜删兜底时没提依赖它的老数据和老用例**：→ 列出依赖它的老数据和老用例，并写明它们之后的行为。
- **反｜方案给的复现步骤在旧代码上其实不红**：→ 方案里写的复现步骤和命令，规划者先在旧代码上自己跑一遍。
- **反｜别人在另一个环境验证过的做法，被写成首选**：目标环境里不成立，失败时的退出码还有危险语义（导致无限重跑）。→ 别的环境里验证过的命令在目标环境仍是【推测】；涉及退出码语义的命令，写出失败时的危害。
- **反｜改"用哪个版本 / 哪个依赖"时没列各版本的能力差异**：修一个回归又引出另一个；追加需求只跑了单测，集成失败到复盘才发现。→ 列出各版本能力差异；追加需求的验收与正式项相同（含集成测试）。
- **正｜先修挡发布的回归，再做增强**：方案把回归、误提交、完整测试全绿排在增强项前面，并写明"到这一步可以交给用户决定发布"。
- **正｜盘点表写成交付物**：方案要求先交"同类调用登记表 / 测试替身清单 / 能引用该资源的入口清单"，执行者据此找出方案没点名的几处，同类问题一次修完。

## 编排、发布、共享资源

- **反｜编排条件没有真值表**：上游被跳过时，"跳过"沿依赖链传下去，结果是假成功。→ 附"上游结果 × 本步是否运行"真值表，并用试跑覆盖。
- **反｜把"替换已发布文件"当成原子操作**：实际是先删后传，读者会在空窗里失败。→ "替换过程中读者看到什么"也是真值表里的一格。
- **正｜对外资源的设计先实测会不会伤到现有工具**：规划时就在临时环境里发现了会让现有命令失败的设计，并改掉了。
- **反｜授权推送没写推送范围**：把不属于本次任务的本地提交一起推了出去。→ 写明推送范围，推送前核对待推送的提交。
- **反｜新增的共享资源漏掉了枚举点**：被当成用户的资源列出、清理。→ 列出所有枚举该类资源的地方。
- **反｜清理用了通配**：误删了不属于本轮的资源。→ 每种共享资源都记基线；清理只按本轮的创建清单逐个删除。
- **反｜旧的常驻进程抢资源**：测试时旧版本的服务或监视进程还在运行，和新代码抢同一批资源。→ 开工前盘点并停掉常驻进程。
- **反｜测试污染用户目录**：在测试里改主目录环境变量，不影响库函数取到的主目录；变量为空时状态写进当前目录；某些命令会把配置写回用户的真实配置文件。→ 会写用户目录的代码路径一律显式注入临时目录。
- **反｜自证只看状态行**：状态显示正常，实际已经坏了。→ 写明用什么真实操作来验证。
- **反｜改了被测试替身包着的函数，方案没点名替身**：→ 新增外部调用或读新字段时，点名要改的替身和夹具。

## 性能与外部资源

- **反｜提速项没先量单项耗时**：搬到别处后反而更慢，目标没达成。→ 关键路径上的每个新步骤先给实测数；目标写明测量条件，并按分解推算。
- **反｜预设了瓶颈**：真正的瓶颈在管道里一个没被怀疑的环节。→ 管道的每一段单独计时。
- **反｜按缓存命中估算收益**：缓存有作用域，实际命中不了。→ 按冷启动的数据估算。
- **反｜默认用逐条接口，没盘点批量渠道**：估算要几十个小时；其实有一个整包，几秒钟就下完了。→ 先盘点所有交付形态（整包、增量包、逐条接口），按实测的墙钟时间选关键路径。
- **反｜限速约束没测就写死，或者短时实验通过就长期使用**：要么全程瓶颈，要么长时间运行后被对方封禁。→ 先小规模实测阈值；验证时长不短于实际运行时长；对没有替代的关键源只用保守档，被拒就立即停止。
- **反｜实验按"配置值"判通过**：配置的速率根本达不到，照样记为通过。→ 通过条件基于实际达到的值；达不到就判"无法达到"。
- **正｜软信号先停**：延迟明显变长时自动降档，没有被封。→ 试探外部限额要有软信号，并先排除本地瓶颈。
- **反｜外部规则没查官方说明就去试探**：反复被封，后来才查到对方公开的配额规则。→ 先查服务方公开的规则和社区转述，再定档位。
- **反｜容差取实测的最大差值**：掩盖了某个来源本身的精度问题。→ 容差按各来源已知的量化规则推出来。
- **反｜为了提速而降低精度，规模大了误差失控**：近似榜单和精确榜单几乎不重合。→ 近似之前先量"近似结果和精确结果的重合度"；算得起就直接用精确目标。
- **反｜过滤或修正类任务没先估影响**：全量重跑以后才发现只影响极少数样本。→ 先用小样本估计会改变多少，再决定要不要全量。

## 不可信输入与信任边界

- **反｜身份可以伪造**：按来源地址识别身份，而运行环境默认允许伪造来源。→ 按每种运行环境逐个列出默认能力，并实测伪造用例。
- **反｜高信任方读取低信任方可写的文件**：→ 一律按不可信输入处理（符号链接、特殊文件、超大文件、伪造内容）。
- **反｜不可信输入只点名了几个高危字段**：审查发现大量字段没人管。→ 逐字段列"字段 → 风险 → 默认处理"。
- **反｜加锁只覆盖了路径前缀**：其他入口能绕过。→ 列出所有能引用该资源的入口。
- **反｜名字规则只给了正则**：`..`、`//` 之类都能通过。→ 凡是会拼进路径或 URL 的名字，都要列出必须拒绝的反例。
- **正｜非官方产物要求可复现构建**：哈希和官方登记的一致才采用。
- **正｜对照实验找出第三方的默认安全策略**：同一服务分别绑定回环地址和全部地址做对照，发现新版本只在回环地址上校验请求头。
- **反｜删命令时漏掉了它的隐含副作用**。
- **正｜不可信来源的数据先隔离、再抽样验证**：单独存一个批次，标上"未验证"；全量做便宜的跨源检查；再按来源分层，用可信渠道抽样复采，一条对不上就整批拒绝。另外用人为篡改的副本检验这套验证本身。

## 收紧类功能与界面

- **反｜收紧时误伤合法链路**：默认拒绝之后，真实客户端依赖的服务被拦；只用最简单的探测工具验证规则不够。→ 每个预设都用真实客户端跑一遍。
- **反｜两套语义重叠的概念并存**：到验收阶段才合并，大量界面问题靠人工纠正。→ 方案阶段就合并概念，审查时同时看视觉和文案。
- **反｜规范里同时写了具体数字和目标值，两者打架**：照抄的具体写法达不到规范要求的目标值，凭印象写的尺寸实测也不对。→ 规范写可量的目标，数字先实测再写；能交给守卫测试的交给守卫。
- **正｜规划时先用替身实测中间件的默认行为**：缓冲、长度上限、中途停顿都写成【实测】，执行时全部证实，还多找出几类问题。

## 数据与研究

- **反｜预注册早于核实外部事实**：→ 先核实规则和阈值再登记，或者预注册只引用核实文档。
- **反｜复合规则里的条件互相蕴含**：→ 列出条件两两之间的包含关系做自检。
- **反｜照搬其他市场或其他领域的"预期方向"**：→ 预期方向引用本领域的证据，没有证据就做双侧检验；方向相反但非常显著的结果要单独报告。
- **反｜结论只写"没通过"**：→ 结论分三类写：能用的 / 该避开的 / 真的没有。
- **反｜口径细节没定义**（月末、年化、取样频率、持有方式、成本、退市或缺失怎么处理）：造成假差异，或者回答的不是用户问的问题。→ 方案里写死所有口径。
- **反｜事后剔除样本**：按未来才知道的事过滤了样本。→ 写明标签缺失的样本怎么处理，并 `grep` 全部实验里有没有同类过滤。
- **反｜优化"最小风险"时选中了"冻结、不可交易"的对象**：→ 可交易性过滤要写成所有方法和对照组共用的口径，并配单测。
- **反｜判定指标的分布尾巴太厚**：严格判定形同虚设。→ 判定用有界、稳健的量；严格判定没过但方向一致时，不改判定，另做一个单格子的前瞻确认。
- **反｜"只是风格"或"有超额"是从别的实验推出来的**：→ 在本实验里直接检验。
- **反｜"能用"的结论没做归因和收缩**：→ 扣除常见因子，并对赢家诅咒做收缩估计。
- **反｜一个时期的验证结论被外推到另一个时期**：→ 在目标时期上抽样验证，否则标为低可信度。
- **反｜多个来源混在一列里，口径不同**：→ 每行带来源，比值在同一来源内计算。
- **反｜抽样数量没考虑命中率**：→ 写成"凑够 N 个有效结果，或者用完请求预算为止"。
- **反｜一致率类的阈值没测就写成 100%**：→ 先用小样本实测，并预留"已知例外清单 + 数量上限"。
- **反｜关卡的检查范围随数据自动扩大**：→ 关卡的范围写死，新增的范围用新的关卡项覆盖。
- **正｜第三个来源做裁决**：两个来源不一致时，第三票能分清谁对谁错。
- **正｜用独立的简单代码复算**：排除了"引擎有错"的怀疑。
- **正｜面向用户的结论做成前瞻存档、纸面跟踪**：这是唯一不受"同一段历史上挑选"污染的检验。
- **正｜第三方旧项目当作"线索"而不是"事实"**：每一条都现场复测后才写进方案。

## 流程、跨会话、长任务

- **反｜FEEDBACK 结构只写在方案末尾**：执行者漏了好几节。→ 规划者直接建好骨架。
- **正｜预建 FEEDBACK 骨架**：执行者每一节都填了，偏差和遗漏各自成节。
- **反｜执行者中途结束，FEEDBACK 一字未写**：→ 把"写 FEEDBACK"做成每一步的验收项。
- **反｜PLAN 中途改了，旧会话没有重读**：→ PLAN 顶部写版本号，执行者每一步开始前核对。
- **正｜版本号让执行者中途接上了修改。**
- **反｜基础设施排在所有计算前面，会话做完一部分就收工**：→ 能最早开跑的长计算排在最前面；规定每次会话的推进量。
- **反｜方案要求"不要停"，但执行者没有自动醒来的机制**：→ 用循环或定时机制自驱，写清每轮的步骤和结束条件。
- **反｜循环里以"等外部条件"为由放空队列**：→ 健康检查里要有一个可以计算的违规判据，不能只写口号。
- **反｜执行者只汇报进度，没汇报后台任务坏了**：→ 每次开工先检查后台任务的健康状态。
- **反｜交付物没单列成验收项，被悄悄漏掉**：→ 每个输出物都单列成验收项，收尾时逐条对照方案原文。
- **反｜看板状态和实际提交对不上、时间戳靠估计**：→ 状态要附提交号，时间戳用命令输出。
- **反｜结论推翻以后，文档没有同步**（反复出现）：→ 收尾时 `grep` 出每个改过的数字和结论的所有出处，逐处同步。
- **反｜复盘只看 FEEDBACK，没核对实际的对外动作**：→ 用版本库记录核对提交、推送这类声明。
- **反｜把"授权发布"当成"豁免检查"**：→ 豁免范围要具体到哪一项、哪个版本。
- **反｜没有方案的连续迭代，交付标准悄悄降级**：→ 删除用户数据之类的功能一律先出方案。
- **反｜真实环境端到端测试，没列出会改用户数据的接口**：→ 列出每个会写用户数据的接口和它波及的范围。
- **反｜会改文件的实验直接在真实仓库上做**：→ 先复制到临时目录。
- **反｜环境规格凭印象写**：→ 用命令现测。
- **反｜跨会话通信用会话名认人**：会话名每次重启都会变，消息发错或发不出去。→ 用不变的对话 ID 认人，发消息前再查出当前的会话名。
- **正｜执行者回报"规范问题"、规划者逐条拍板**：规范因此比第一版扎实。规范里的每个"默认值"，规划者都要先量一次。
