# PLAN.md 模板

按需删减章节，但「执行须知」「硬约束」「测试方案」「实施步骤」「交付说明」不能省。正文力求精炼：表格优先，每条结论都标注依据。

```markdown
# <专项名称>：<一句话目标>

> **执行须知**（执行者只会收到“基于本文执行”这一句话，所有要求都在本文中）
> 1. 任务：<测试 → 整改 → 复核 → 提交 → 合并/推送 X>。全程自主推进，不需要中途向用户确认；遇到本文没有覆盖的取舍，按“<优先级>”自行决定，并写进交付说明。
> 2. 动手前先通读本文和 <AGENTS.md 及子目录说明>。第二节是硬约束。
> 3. 结论以实测为准：标【实测】的已于 <日期> 在 <环境规格> 上复现，标【源码】的需要用测试证实。先写失败用例再修。
> 4. 可以用 <模型> 子 agent 并行工作，但所有事实和结论都要亲自复核。
> 5. 执行中持续写同目录的 `FEEDBACK.md`（结构见第九节），发现偏差或踩坑时当场记下；按「实施步骤」推进，结束时按「交付说明」输出。

## 一、结论
<3～6 行：现状判断、根因、方向。已与用户确认的产品决策写在这里。>

## 二、硬约束
- 核心目标：<用户最在意的事>
- 不能退化的能力：<…>
- 态度：<例如：清理历史债，不留兼容层>
- 授权：已授权 <…>；未授权 <…>（只写进交付说明）
- 版本：<改成多少 / 不改>
- 资源：<本机规格>；只验证 <架构>；并发上限 <N>；可以自行安装需要的工具
- 敏感信息：<token 来源；禁止打印 / 提交；使用临时 home>

## 三、现状 / 缺陷清单
| # | 问题 | 依据【实测/源码】 | 影响 |

## 四、目标设计
### 用户视角（我想… → 命令）
### 架构与关键决策（附理由；未实测的假设 + 失败时的备选方案）

## 五、测试方案
- L1 单元：<…>（会写用户目录的路径一律注入临时 home）
- L2 真实依赖集成（含破坏性场景）：<表格：用例 / 步骤 / 期望>
- L3 质量 / 仿真对比：<修改前后的数据>
- L4 真实端到端：<真实 LLM / 真实浏览器 / 截图 / 模拟键鼠>
- L5 新手试用：只给新子 agent 文档，迭代到一次通过
- 必验：第三方库的安全默认值 <…>
- 留给用户的部分（仅限做不到的）：<…，以及原因>

## 六、文档要求
<目标篇幅、结构，以及需要同步修改的文件>

## 七、实施步骤
1. <步骤> —— 验收：<…>
…
N. 复核（代码审查）→ 提交前检查 → 提交 / 合并 / 推送 <按授权>

## 八、交付说明须包含
- 缺陷逐项状态（已修复并附回归用例 / 无法复现 / 不修及原因）
- 测试结果；跳过项和未实测项
- 需要用户授权或亲自做的事（发布副作用：扫描允许列表、产物体积、发布顺序）
- 破坏性变化

## 九、FEEDBACK.md 结构（写给出方案的 agent，只写高价值内容，每条都要有依据）
一、被实测证实的部分　二、计划与现实的偏差（计划要求 X → 实测 Y → 改成 Z 及代价）　三、计划遗漏（最重要的放在最前）　四、测试结果摘要（数字、耗时、跳过项）　五、代码审查采纳情况　六、仍未实测 / 遗留（附验证方式或备选方案）　七、对下次出方案的建议（可泛化的经验）
```
