# plan-handoff：出方案 → 一句话执行 → 反馈 → 复盘

目的：聪明的 agent 负责调研和设计，执行的 agent 只收到一句话也能独立做完，用户几乎不用亲自测试。

本 skill 只写**与项目无关的方法论**，目录可以整个拷给别人用，不会泄露任何项目信息。三层分工：
- **skill 目录**（本目录）：通用原则、模板、通用脚本。`references/cases.md` 只收**脱敏后**的通用案例：不写项目名、产品名、命令、路径、数据源名、研究内容。
- **项目本地案例** `<项目>/.claude/plan-handoff.local/cases.md`：带细节的原始案例，不随 skill 分享。出方案和复盘时如果存在就读。
- **项目事实**（命令、路径、运行时差异）写进项目的 AGENTS.md 或 CLAUDE.md。

出方案时，把原则落实成本项目的具体做法，那些细节写进 PLAN，不写回这里。

先判断自己的角色，只读对应的那一节。

---

## 角色一：出方案（Planner）

产物：`./temp/<短横线命名的专项目录>/PLAN.md`（确认 `temp/` 已被 git 忽略；没有的话在交付时告诉用户）。结构按 `references/plan-template.md`。**规划者对执行质量负责**：执行者绕过的要求，多半是方案没有写成可检查的交付物。

### 步骤

1. **读规矩**：项目的 AGENTS.md / CLAUDE.md，以及与任务相关的子目录说明。
2. **调研代码**：读核心实现、测试、文档、配置。大文件按符号定位，不要整文件读完。
3. **本地实测**：用最小实验验证最可疑的点，每条结论标注【实测】【源码】或【推测】，并记下环境规格。
4. **在线调研**：只在第三方行为影响设计时做。
5. **只问产品决策**：只有用户能决定、而且会改变方案走向的问题，集中问一次，并给出推荐项。技术细节自己定。
6. **写 PLAN.md**：对照下面的检查清单逐条落实。用户后续追加的要求写进 PLAN，不要写进给用户的提示词。动笔前可以翻一下 `references/cases.md` 和项目本地的 `.claude/plan-handoff.local/cases.md`（如果有），看有没有类似的情境。
7. **交付**：三五行核心结论，加上一句话的执行提示词：`基于 ./temp/<目录>/PLAN.md 执行`。

### 检查清单（每条都要落实，或者明确写“不适用”）

**执行条件**

- [ ] **执行须知**：执行者只会收到一句话；全程自主；没覆盖到的取舍按什么优先级决定；先读哪些文件；执行中持续写 FEEDBACK。
- [ ] **授权边界写死**：哪些对外动作已授权、哪些没有；版本号改不改。人工门禁的豁免要写明具体范围，“授权做某个动作”不等于“豁免某项检查”。授权推送时写明推送范围，推送前先核对待推送的提交（本地可能有不属于这次任务的提交）。
- [ ] **环境与隔离**：本机规格（用命令现测，不凭印象）、能装什么工具、并发上限。会改文件的实验先复制到临时目录做。会写用户真实目录或配置的路径，一律注入临时目录，或者写明执行后要恢复。会碰到的每一种共享资源（每个运行时、每个存储）开工前都要记基线；清理只按本次登记的创建清单删除，禁止通配批量删除。自证“东西还活着”要用真正的操作去验证，不能只看状态行。写明密钥从哪里来，并禁止打印、禁止提交。

**问题与设计**

- [ ] **硬约束**：用户最在意的目标、不能退化的能力、对历史包袱的态度、项目规范里的关键条目。
- [ ] **现状 / 缺陷清单**：每条带证据标注和影响，共性问题和个别问题分开写。每个缺陷先找到根因类别，再列出同类的所有实例，一起修，不要只修用户报告的那一个；兜底和降级路径不能比原问题更糟，例如悄悄丢掉用户数据。
- [ ] **目标设计**：先从用户视角写，再写架构；关键决策写明理由；每个没实测的假设都要写出失败时的备选方案。获取外部资源（数据、产物、依赖）时，先盘点它的所有交付形态（整包、增量包、逐条接口），按实测的墙钟时间和"哪个产物会卡住下游"排出关键路径。限速和并发这类约束，先实测再定档位，不要凭印象写死；验证时长要不短于实际运行时长。对没有替代、又没公开限额的关键源只用保守档，服务端一拒绝就立即停止，不要降档继续。写清楚每个关键源不可用时，各项交付物降级成什么。
- [ ] **实验按实际自变量判定**：限速、并发、阈值这类实验，通过条件要基于实际达到的值（例如实测速率），而不是配置值；达不到目标值的，判为"无法达到"，不判"通过"。
- [ ] **收益先量后写**：优化项要有改动前的数据，否则标【推测】并写出放弃门槛。放进关键路径的新步骤、被搬到别处的步骤，都要先有单项实测耗时，因为换个地方执行未必更快。目标时长要写明在什么条件下测量，并按分解推算能否达到。性能问题不要先假定瓶颈在哪一段：管道 `A | B | C` 要分别量 A 单独、A 接丢弃、A | B。

**专项审查（按需）**

- [ ] **信任边界**：低信任方能控制高信任方的哪些资源？协议本身提供了哪些能力？每份输入由谁写入？“按身份识别”的设计里，这个身份谁能伪造？不可信输入（导入的文件、别人的配置）要逐字段列出“字段 → 风险 → 默认处理 / 谁确认”，不能只点名几个高危字段。每一条都写成“越界被拒”的回归用例。
- [ ] **依赖与默认值**：第三方库或平台的安全默认值、换版本后新增的默认策略，都列为必验项。新依赖说明来源和信任依据；删除依赖或命令之前，查清全部调用方和隐含副作用。
- [ ] **收紧类功能**（默认拒绝、白名单、限流）：先列出会被误伤的合法链路，写明放行或缓解方式；被拒绝时用户能立刻看到原因。
- [ ] **编排**（依赖链、条件执行、并发组）：附一张“上游结果 × 本步是否运行”的真值表，写清排队和取消的语义，并用真实运行覆盖“上游被跳过”“排队被顶掉”这类格子。静态审查替代不了试跑。
- [ ] **状态与一致性**（缓存、增量、重试、合并写入）：逐个问每个失效条件在稳态下多久触发一次；同名字段在不同模式下的含义要分别写清；“没收到确认”不等于“没送达”，恢复或重试之前要按幂等键对一次账；参数边界用真实调用方能产生的极值核对。用户的意图（停止、暂停、取消）要落盘，并逐条核对它在重启之后、下一次操作之后是否仍然成立，规则之间不能互相矛盾。
- [ ] **改核心流程**：盘点测试替身、注入点和常驻进程，把改造量写进计划；新增的共享资源，要列出所有枚举对象的地方，写清幂等和竞态规则；加锁 / 闸门时，要列出所有能引用该资源的入口（路径参数、请求体里的名字、清理与定时任务），不只是路径前缀。
- [ ] **界面**（有前端时）：复用现有范式，同类控件只用一个组件；截图并排对比；文案是否一句话、没有术语。
- [ ] **发布副作用**（涉及产物时）：安全扫描、体积上限、版本号同步位置、发布顺序；需要授权的步骤写进交付说明。
- [ ] **临时措施**：写出添加和删除两步，并用断言保证交付时已经删除；同时写明临时期间这条断言怎么放行、由谁删除放行。

**验证**

- [ ] **TDD 写成交付物**：每条新用例都要有红灯证据（在旧代码上的失败输出），记录在 FEEDBACK 的红灯证据表里，附上可复现的命令和原始失败输出片段（复盘时抽查重跑）。红灯由执行者亲自复现；只因“模块不存在”而失败不算红灯，要用变异验证补证（故意改坏一处关键逻辑，确认有用例失败）。关键约束要列出必做的变异清单。旧代码上本来就该通过的守卫用例（防回归）单列，不要求红灯，用变异证明它能失败。
- [ ] **分层测试**：单元 → 真实依赖集成（含破坏性场景）→ 改动前后的数据对比 → 真实端到端 → 必要时让新手子 agent 只看文档试用（走用户真实入口，改完文档再试一次）。包装外部进程或协议的读写端，第一步先用真实依赖跑通最小闭环，再铺假替身的单测（替身模拟不出“不读完就堵住”“下游断开”这类行为）。最小闭环要带上真实环境里同时存在的其他访问者（后台轮询、定时任务），死锁往往只在它们在场时出现。设计有意改变行为时，列出哪些验收判据要跟着改，以及改前改后的写法；修复前后的对比要用同一套能兼容新旧接口的工具。先跑基线再动代码；“成功”类断言要落到“真的生效”，不能只看退出码。
- [ ] **检验的检验**：任何检测器、关卡、灵敏度用例，都要有一条"把被测函数换成恒等或坏的实现，检验必须失败"的用例。注入的错误要作用在被测流程的输入上，不能绕过被测流程。
- [ ] **自测优先，不让用户测**：能自动化的都写进方案。只有确实做不到的才留给用户，并写明原因。要警惕测试工具本身伪装出的环境状态，以及测试替身被真实输入意外触发；关键环境要先验证测试手段确实有效，再拿它下结论。
- [ ] **用成果完成一次真实任务**作为验收（做的是工具或流程，就用它真实跑一遍），自测发现不了的缺陷往往在这一步暴露。
- [ ] **外部状态用权威来源探测**，不依赖本机的镜像、代理等配置。

**收尾**

- [ ] **跨会话方案的节奏**：方案如果要跨多个会话完成，要写明每次会话的推进量（例如"后台不能空闲"）、开工时先检查后台任务的健康状态（不只是看进度），并把能最早开跑的长计算排在基础设施前面。长时间无人值守的方案要明确"自动续跑"的机制（例如 Claude Code 的 `/loop`，由模型自己安排下一次醒来），并写清：每一轮做什么、什么时候安排下一次醒来、什么时候才结束循环；需要用户决定的事列进待办，按保守默认值继续，不要停下来等。
- [ ] **实施步骤**：每步都有验收标准；提交与合并按项目规范。收尾时，对本轮更新或推翻过的每个数字和结论，`grep` 出所有写过它的地方逐处同步。
- [ ] **交付要求**：FEEDBACK 的结构写在 PLAN 里，并在同目录建好 FEEDBACK 骨架（全部标题，每节先写“无”），执行者只往里填，不会漏节；在对话里给出简要结论。每个实施步骤的验收项里都要包含"FEEDBACK 已记下本步的红灯、偏差和数字"，这样执行中途中断也不会丢失信息。

## 角色二：执行（Executor）

收到“基于 ./temp/<目录>/PLAN.md 执行”时：

1. 完整读 PLAN 和它要求读的文件。PLAN 可能在执行中途被追加修改：每一步开始前核对 PLAN 顶部的版本号（或修改时间），变了就先读变化的部分。PLAN 的执行须知和硬约束优先于你的默认习惯，但不能凌驾于用户在对话里的明确指令和安全规则。
2. 先核实 PLAN 的结论，把缺陷转成失败用例；复现不了的如实标注，不要硬修。
3. 按步骤自主推进。能自己测的绝不留给用户。红灯证据要亲自跑，不能用子 agent 的说法代替。
4. 子 agent 的临时检出用完即删；要保留的产物写到主检出的绝对路径。
5. **边做边写** FEEDBACK（往规划者建好的骨架里填；没有骨架就复制 `references/feedback-template.md`）。只记高价值内容：计划错在哪、遗漏了什么、下次该怎么写。
6. 执行中用户追加的需求（例如“顺手修一下”）按同样的标准做：找根因和同类实例、留红灯证据、记进 FEEDBACK。范围明显超出 PLAN 时，先在 FEEDBACK 里写清楚，留给规划者出新方案。
7. 对外动作严格按授权边界执行，授权范围外的只写进交付说明。
8. 结束时说明：做了什么、测试结果、没验证的部分、需要用户做的事。

9. **有规划者会话在线监督时**（见下面的"跨会话监督"）：每完成一个阶段、遇到需要规划者决定的事，或者结束循环时，主动给规划者会话发一条 5 行以内的消息：目录、PLAN 版本、完成了什么、FEEDBACK 新增要点、阻塞项。没有就不发。收到规划者的指令，按 PLAN 版本的流程处理（先读变化的部分）。

## 跨会话监督（可选，规划者和执行者同时在线时）

规划者贵、执行者便宜，所以规划者不要轮询，靠执行者来叫：

- **事件触发为主**：执行者在阶段完成、需要决策、结束循环时给规划者发短消息。规划者收到后再读 FEEDBACK 和 PROGRESS，必要时改 PLAN（版本号加 1），然后给执行者发一句话的指令。
- **兜底检查为辅**：规划者设一个间隔较长的定时检查（几个小时一次），只用最便宜的方式看：文件修改时间、最近的提交、队列状态。没变化就什么也不做，防止漏消息或执行者卡死。不要高频轮询。
- **改动对用户可见**：规划者发出的每条指令，都在自己的会话里写明发给谁、发了什么。用户可以随时叫停。
- **权限不外借**：不要让执行者去做规划者自己没被授权的事。
- **会话名不固定**：会话名每次启动或恢复都会重新分配。双方都不要把对方的名字写死：规划者每次重启后，先用 ListAgents 查到自己的新名字，主动发给各执行者；执行者发消息前先 ListAgents，找不到规划者时不要猜，把汇报写进 FEEDBACK 和 PROGRESS，等规划者的兜底检查读到。
- **认人用对话 ID，不用会话名**：对话 ID（`--resume` 用的那个）不会变。`python3 .claude/skills/plan-handoff/scripts/peers.py` 会列出本机在跑的会话：会话名 ↔ 对话 ID ↔ 进程号（数据来自 `~/.claude/sessions/<进程号>.json`）。收到的消息里 `from="…/cc-socks/<进程号>.sock"` 的进程号，可以用它对上对话 ID。PLAN 里写对方的**对话 ID**，发消息前用这个脚本查出它当前的会话名。

## 角色三：复盘（Retro）

用户带着 FEEDBACK 回来时：

1. 先问**是不是方案的问题**：执行者绕过了要求、做错了取舍、漏掉了场景，先检查方案有没有把它写成可检查的交付物。规划者的问题由规划者认领，不要算到执行者头上。
2. **抽查**：按红灯证据表重跑一条；执行者声称“产物可用”的，打开一个产物看实际内容。
3. 分拣：
   - **项目事实**（读代码看不出来的约束）→ 补进项目的 AGENTS.md（执行者补过的就核对一下）。
   - **方案确实写得不好，或者某种写法明显奏效** → 在项目本地的 `.claude/plan-handoff.local/cases.md` 追加一条带细节的案例：情境 → 方案怎么写的 → 结果 → 抽出的原则。原则能泛化的，再用**不含任何项目信息**的说法，补一条到 skill 的 `references/cases.md`。写之前自查：不能出现项目名、产品名、路径、命令、数据源名、研究对象。
   - **原则本身有缺口**（多个案例反复指向同一个问题，或者现有条目明显挡不住）→ 才修改 SKILL.md 的检查清单。用抽象的说法改，**不写项目名、命令、路径**；优先改写或合并已有条目，不要新增。
   - **一次性事实** → 不沉淀。
4. 遗留问题需要新一轮工作时，按“角色一”出新方案。
5. 汇报：哪些问题认领为方案的问题，改了哪些文件的哪几条，建议的下一步。
