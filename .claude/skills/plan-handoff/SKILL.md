# plan-handoff：出方案 → 一句话执行 → 反馈 → 复盘

目的：聪明的 agent 负责调研和设计，执行的 agent 只收到一句话也能独立做完，用户几乎不用亲自测试。

本 skill 只写**与项目无关的方法论**。项目里的具体事实（命令、路径、运行时差异）写进项目的 AGENTS.md；带着具体细节的正反面历史案例放在 `references/cases.md`。出方案时把原则落实成本项目的具体做法，那些细节写进 PLAN，不写回这里。

先判断自己的角色，只读对应的那一节。

---

## 角色一：出方案（Planner）

产物：`./temp/<短横线命名的专项目录>/PLAN.md`（确认 `temp/` 已被 git 忽略；没有的话在交付时告诉用户）。结构按 `references/plan-template.md`。**规划者对执行质量负责**：执行者绕过的要求，多半是方案没有写成可检查的交付物。

### 步骤

1. **读规矩**：项目的 AGENTS.md / CLAUDE.md，以及与任务相关的子目录说明。
2. **调研代码**：读核心实现、测试、文档、配置。大文件按符号定位，不要整文件读完。
3. **本地实测**：用最小实验验证最可疑的点，每条结论标注【实测】【源码】或【推测】，并记下环境规格。
4. **在线调研**：只在第三方行为影响设计时做。
5. **只问产品决策**：只有用户能决定、而且会改变方案走向的问题，集中问一次，并给出推荐项。技术细节自己定。
6. **写 PLAN.md**：对照下面的检查清单逐条落实。用户后续追加的要求写进 PLAN，不要写进给用户的提示词。动笔前可以翻一下 `references/cases.md`，看有没有类似的情境。
7. **交付**：三五行核心结论，加上一句话的执行提示词：`基于 ./temp/<目录>/PLAN.md 执行`。

### 检查清单（每条都要落实，或者明确写“不适用”）

**执行条件**

- [ ] **执行须知**：执行者只会收到一句话；全程自主；没覆盖到的取舍按什么优先级决定；先读哪些文件；执行中持续写 FEEDBACK。
- [ ] **授权边界写死**：哪些对外动作已授权、哪些没有；版本号改不改。人工门禁的豁免要写明具体范围，“授权做某个动作”不等于“豁免某项检查”。
- [ ] **环境与隔离**：本机规格、能装什么工具、并发上限。会写用户真实目录或配置的路径，一律注入临时目录，或者写明执行后要恢复。写明密钥从哪里来，并禁止打印、禁止提交。

**问题与设计**

- [ ] **硬约束**：用户最在意的目标、不能退化的能力、对历史包袱的态度、项目规范里的关键条目。
- [ ] **现状 / 缺陷清单**：每条带证据标注和影响，共性问题和个别问题分开写。每个缺陷先找到根因类别，再列出同类的所有实例，一起修，不要只修用户报告的那一个；兜底和降级路径不能比原问题更糟，例如悄悄丢掉用户数据。
- [ ] **目标设计**：先从用户视角写，再写架构；关键决策写明理由；每个没实测的假设都要写出失败时的备选方案。
- [ ] **收益先量后写**：优化项要有改动前的数据，否则标【推测】并写出放弃门槛。

**专项审查（按需）**

- [ ] **信任边界**：低信任方能控制高信任方的哪些资源？协议本身提供了哪些能力？每份输入由谁写入？“按身份识别”的设计里，这个身份谁能伪造？每一条都写成“越界被拒”的回归用例。
- [ ] **依赖与默认值**：第三方库或平台的安全默认值、换版本后新增的默认策略，都列为必验项。新依赖说明来源和信任依据；删除依赖或命令之前，查清全部调用方和隐含副作用。
- [ ] **收紧类功能**（默认拒绝、白名单、限流）：先列出会被误伤的合法链路，写明放行或缓解方式；被拒绝时用户能立刻看到原因。
- [ ] **状态与一致性**（缓存、增量、重试、合并写入）：逐个问每个失效条件在稳态下多久触发一次；同名字段在不同模式下的含义要分别写清；“没收到确认”不等于“没送达”，恢复或重试之前要按幂等键对一次账；参数边界用真实调用方能产生的极值核对。
- [ ] **改核心流程**：盘点测试替身、注入点和常驻进程，把改造量写进计划；新增的共享资源，要列出所有枚举对象的地方，写清幂等和竞态规则。
- [ ] **界面**（有前端时）：复用现有范式，同类控件只用一个组件；截图并排对比；文案是否一句话、没有术语。
- [ ] **发布副作用**（涉及产物时）：安全扫描、体积上限、版本号同步位置、发布顺序；需要授权的步骤写进交付说明。
- [ ] **临时措施**：写出添加和删除两步，并用断言保证交付时已经删除。

**验证**

- [ ] **TDD 写成交付物**：每条新用例都要有红灯证据（在旧代码上的失败输出），记录在 FEEDBACK 的红灯证据表里，附上可复现的命令和原始失败输出片段（复盘时抽查重跑）。红灯由执行者亲自复现；只因“模块不存在”而失败不算红灯，要用变异验证补证（故意改坏一处关键逻辑，确认有用例失败）。关键约束要列出必做的变异清单。
- [ ] **分层测试**：单元 → 真实依赖集成（含破坏性场景）→ 改动前后的数据对比 → 真实端到端 → 必要时让新手子 agent 只看文档试用（走用户真实入口，改完文档再试一次）。先跑基线再动代码；“成功”类断言要落到“真的生效”，不能只看退出码。
- [ ] **自测优先，不让用户测**：能自动化的都写进方案。只有确实做不到的才留给用户，并写明原因。要警惕测试工具本身伪装出的环境状态，以及测试替身被真实输入意外触发；关键环境要先验证测试手段确实有效，再拿它下结论。
- [ ] **用成果完成一次真实任务**作为验收（做的是工具或流程，就用它真实跑一遍），自测发现不了的缺陷往往在这一步暴露。
- [ ] **外部状态用权威来源探测**，不依赖本机的镜像、代理等配置。

**收尾**

- [ ] **实施步骤**：每步都有验收标准；提交与合并按项目规范。
- [ ] **交付要求**：FEEDBACK 的结构写在 PLAN 里，并在对话里给出简要结论。

## 角色二：执行（Executor）

收到“基于 ./temp/<目录>/PLAN.md 执行”时：

1. 完整读 PLAN 和它要求读的文件。PLAN 的执行须知和硬约束优先于你的默认习惯，但不能凌驾于用户在对话里的明确指令和安全规则。
2. 先核实 PLAN 的结论，把缺陷转成失败用例；复现不了的如实标注，不要硬修。
3. 按步骤自主推进。能自己测的绝不留给用户。红灯证据要亲自跑，不能用子 agent 的说法代替。
4. 子 agent 的临时检出用完即删；要保留的产物写到主检出的绝对路径。
5. **边做边写** FEEDBACK（结构按 PLAN；PLAN 没写就用 `references/feedback-template.md`）。只记高价值内容：计划错在哪、遗漏了什么、下次该怎么写。
6. 执行中用户追加的需求（例如“顺手修一下”）按同样的标准做：找根因和同类实例、留红灯证据、记进 FEEDBACK。范围明显超出 PLAN 时，先在 FEEDBACK 里写清楚，留给规划者出新方案。
7. 对外动作严格按授权边界执行，授权范围外的只写进交付说明。
8. 结束时说明：做了什么、测试结果、没验证的部分、需要用户做的事。

---

## 角色三：复盘（Retro）

用户带着 FEEDBACK 回来时：

1. 先问**是不是方案的问题**：执行者绕过了要求、做错了取舍、漏掉了场景，先检查方案有没有把它写成可检查的交付物。规划者的问题由规划者认领，不要算到执行者头上。
2. 分拣：
   - **项目事实**（读代码看不出来的约束）→ 补进项目的 AGENTS.md（执行者补过的就核对一下）。
   - **方案确实写得不好，或者某种写法明显奏效** → 在 `references/cases.md` 追加一条案例：情境 → 方案怎么写的 → 结果 → 抽出的原则。
   - **原则本身有缺口**（多个案例反复指向同一个问题，或者现有条目明显挡不住）→ 才修改 SKILL.md 的检查清单。用抽象的说法改，**不写项目名、命令、路径**；优先改写或合并已有条目，不要新增。
   - **一次性事实** → 不沉淀。
3. 遗留问题需要新一轮工作时，按“角色一”出新方案。
4. 汇报：哪些问题认领为方案的问题，改了哪些文件的哪几条，建议的下一步。
